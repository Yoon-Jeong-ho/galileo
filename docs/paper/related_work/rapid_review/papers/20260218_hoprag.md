# HopRAG: Multi-Hop Reasoning for Logic-Aware Retrieval-Augmented Generation

- Year: 2025
- Venue: arXiv (cs.IR, cs.CL)
- Authors: Hao Liu; Zhengren Wang; Xi Chen; Zhiyu Li; Feiyu Xiong; Qinhan Yu; Wentao Zhang
- URL: https://arxiv.org/abs/2502.12442
- BibTeX key (if we add it): hoprag2025liu

## One-sentence takeaway

HopRAG turns “imperfect top-k retrieval” into a multi-hop graph exploration problem by linking passages with LLM-generated pseudo-queries and traversing/pruning via LLM reasoning to improve multi-hop QA retrieval and answer quality.

## What problem does it solve?

- Standard sparse/dense retrievers optimize lexical/semantic similarity, not *logical relevance*, so for multi-hop QA they:
  - miss needed supporting passages (low recall), and/or
  - retrieve many passages that are only indirectly relevant (low precision).
- The paper claims that many retrieved passages are within a few hops of the true supporting facts, suggesting graph traversal can recover the needed evidence.

## What is the core method / protocol?

- **Indexing: build a passage graph**
  - Vertices: text chunks / passages.
  - Directed edges: “logical connections” represented by **LLM-generated pseudo-queries** that connect a *raiser* passage to a *solver* passage (their term).
  - Construction uses query simulation + edge merging (details not fully captured from the truncated HTML, but the key idea is pseudo-query-as-edge).
- **Retrieval: retrieve → reason → prune**
  - Start with initial top-k candidates from a conventional retriever (lexical/semantic).
  - **Explore multi-hop neighbors** in the passage graph.
  - Use **LLM reasoning guided by pseudo-queries** to decide which hops/candidates are truly relevant.
  - **Prune** irrelevant branches to stay within a budget.

## What are the key metrics?

- Retrieval quality: precision/recall/F1 of retrieving supporting passages (multi-hop QA setting).
- Downstream QA: answer quality metrics on multi-hop benchmarks (not fully enumerated in the snippet; likely EM/F1 depending on dataset).

## What are the main results?

- On multi-hop QA benchmarks (HotpotQA, 2WikiMultiHopQA, MuSiQue), they report that the retrieve-reason-prune mechanism:
  - expands retrieval scope via logical connections,
  - improves retrieval F1,
  - improves final answer quality.
- Claimed improvements (from intro): **+20.97% retrieval F1** and **+36.25% answer metric** vs conventional IR baselines (exact baseline set not extracted here).

## How is this similar to GALILEO?

- Both are motivated by limitations of one-shot similarity retrieval for complex reasoning.
- Both effectively introduce *structured exploration* and *reasoning signals* to improve evidence selection for downstream generation/decision.

## How is this different from GALILEO?

- HopRAG is explicitly a **RAG retrieval/indexing framework** (passage graph + traversal) rather than a model-robustness / multi-turn behavior evaluation setup.
- It relies on **LLM calls at indexing (pseudo-query generation)** and at retrieval time (reason/prune), so it is more like an LLM-in-the-loop IR system.

## Where GALILEO is stronger / cleaner (if true)

- If GALILEO’s focus is evaluation/robustness, it can more cleanly separate *retrieval errors* from *reasoning/decision errors*, whereas HopRAG blends retrieval with LLM reasoning (harder to attribute gains).

## Where GALILEO is weaker / needs to improve

- If GALILEO currently assumes a fixed retriever or single-step evidence, HopRAG suggests a concrete mechanism (graph + multi-hop traversal) that could be a strong baseline/ablation point.
