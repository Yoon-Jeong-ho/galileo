# LLM-A*: Large Language Model Enhanced Incremental Heuristic Search on Path Planning

- Year: 2024
- Venue: Findings of ACL: EMNLP 2024 (arXiv:2407.02511)
- Authors: Silin Meng; Yiwei Wang; Cheng-Fu Yang; Nanyun Peng; Kai-Wei Chang
- URL: https://arxiv.org/abs/2407.02511
- BibTeX key (if we add it): llm_a_star_meng_2024
- Tags: path-planning; heuristic-search; llm; hybrid

## One-sentence takeaway

Augments A* with LLM-suggested intermediate waypoints ("targets") and a modified f-cost to cut node expansions / memory dramatically while preserving 100% path validity, at the cost of slightly longer paths.

## What problem does it solve?

- Classic optimal search (A* and variants) becomes computationally and memory expensive as map/state space scales.
- Pure LLM path generation has global intuition but frequently produces invalid/colliding/incomplete paths due to weak fine-grained spatial reasoning.
- Goal: combine LLM global guidance with A*'s validity guarantees to improve efficiency in larger continuous-ish planning settings.

## What is the core method / protocol?

- Proposes **LLM-A***: keep the A* search loop (OPEN/CLOSED, neighbor expansion), but:
  - Query an LLM once to produce a **TARGET list T**: a sequence of waypoints from start to goal (with constraints: must contain start+goal; remove any targets that lie inside obstacles).
  - Maintain a current target `t` from T; when the search reaches `t`, advance to next target.
  - When `t` updates, **recompute f-costs in OPEN** using an augmented objective:
    - f(s) = g(s) + h(s) + cost(t, s)
    - Intuition: bias the frontier toward the current LLM waypoint, reducing irrelevant exploration.
- Prompting variants for generating T:
  - few-shot prompting (5 demonstrations)
  - chain-of-thought (3-shot)
  - recursive path evaluation (RePE; incremental generate + evaluate steps)

## What are the key metrics?

(Reported relative to baseline A* = 100)

- **Operation ratio** (proxy for time complexity; lower is better)
- **Storage ratio** (proxy for memory; lower is better)
- **Relative path length** (vs optimal; lower is better)
- **Valid path ratio** (success rate; higher is better)
- Scalability: growth of ops/storage as environment scale increases.

## What are the main results?

- Dataset: 100 manually selected 50x30 maps, each with 10 start/goal pairs (1000 total samples). Environment described as continuous but executed on discretized points/actions.
- On the main map size (50x30):
  - **LLM-only** methods have low validity (roughly 8-16% valid path ratio depending on model/prompt), and longer-than-optimal paths (~111-184% relative length).
  - **LLM-A*** retains **100% valid path ratio** across settings.
  - With GPT-3.5:
    - ops ~57% of A*, storage ~75% of A*, path length ~102% of optimal.
  - With Llama3:
    - ops ~45% of A*, storage ~64% of A*, path length ~102% of optimal.
  - Weighted A* baseline (dynamic WA*, w=2 with decay) improves ops/storage vs A* but is worse than LLM-A* in their table.
- Scalability: claims A* ops/storage grow exponentially with environment scaling, while LLM-A* is near-linear (plots summarized in Fig. 3).

## How is this similar to GALILEO?

- Uses an **external model to provide global guidance / high-level structure** while relying on a classical algorithm for correctness.
- Fits the pattern of **hybrid systems**: learned component proposes subgoals; symbolic/algorithmic component guarantees feasibility.
- Emphasizes efficiency gains through better guidance rather than purely learning an end-to-end planner.

## How is this different from GALILEO?

- Focus is narrowly on **2D path planning / heuristic search**; not a general interactive agent protocol.
- Learned component is used primarily as a **waypoint generator**; does not incorporate richer observation histories, tool use, or multi-step task decomposition beyond waypoints.
- Evaluation is on synthetic map benchmarks; may not test robustness issues common in real embodied settings.

## Where GALILEO is stronger / cleaner (if true)

- If GALILEO includes explicit uncertainty handling / verification loops, it may offer more principled guardrails than "single LLM call to produce targets".
- If GALILEO is designed for broader tasks (not only navigation), its protocol generality could be stronger.

## Where GALILEO is weaker / needs to improve

- If GALILEO currently lacks a clean story for integrating classical search/planning primitives, this paper is a concrete example worth contrasting.
- If GALILEO claims efficiency/scaling benefits, this offers a directly comparable efficiency narrative (ops/memory ratios) that GALILEO may need to match with equally clear metrics.
