# Open Vocabulary Monocular 3D Object Detection

- Year: 2025
- Venue: 3DV 2026 (arXiv:2411.16833v2)
- Authors: Jin Yao, Hao Gu, Xuweiyi Chen, Jiayun Wang, Zezhou Cheng
- URL: https://arxiv.org/abs/2411.16833
- BibTeX key (if we add it): Yao2025OVMono3D
- Tags: open-vocabulary, monocular, 3d-detection, 2d-to-3d lifting, foundation-models, depth, evaluation-metrics

## One-sentence takeaway

Decouple OV monocular 3D detection into (open-vocab) 2D detection + class-agnostic 2D-to-3D lifting, and evaluate with a “target-aware” protocol that reduces missing-label / naming-ambiguity artifacts.

## What problem does it solve?

- Defines/studies **open-vocabulary monocular 3D object detection**: detect *novel* categories in **metric 3D** from a **single RGB image**.
- Addresses two practical blockers:
  - **Training/generalization** with limited 3D box annotations (vs abundant 2D data).
  - **Evaluation brittleness** due to missing 3D labels and category naming ambiguities (e.g., “table” vs “desk”).

## What is the core method / protocol?

Two complementary approaches:

- **OVMono3D-GEO (training-free baseline)**
  - Run open-vocab 2D detector (they default to Grounding DINO) → boxes + labels.
  - Get instance masks (e.g., SAM) and metric depth (e.g., UniDepthv2) → unproject masked pixels to a point cloud using intrinsics.
  - Fit oriented 3D boxes via PCA orientation + DBSCAN outlier removal + centroid/dimensions from cleaned points.
  - Key limitation: sensitive to occlusion/noisy depth; tends to bias size/pose from visible parts.

- **OVMono3D-LIFT (learning-based)**
  - Stage 1: off-the-shelf OV 2D detector provides 2D ROIs (for novel categories too).
  - Stage 2: **class-agnostic** “lift head” predicts 3D box attributes from:
    - visual ROI features from a pretrained image encoder (DINOv2 + FPN) and
    - geometric ROI features from a pseudo-depth-derived point map (ROI-pooled 3×7×7 point features).
  - Trained on Omni3D base categories with a Cube R-CNN-style 3D box loss, but without class-specific size priors.
  - Variant **LIFT\*** removes the depth module to isolate the value of geometry.

Evaluation protocol:

- **Target-aware evaluation**: for each test image, prompt the OV 2D detector only with category names that appear in that image’s ground-truth annotations.
  - Intended to reduce false negatives from missing labels and reduce false positives from near-synonym predictions.

## What are the key metrics?

- 3D Average Precision (AP3D) over IoU3D thresholds (Omni3D protocol); they report multiple IoU thresholds (e.g., 0.15 / 0.25 / 0.5 in some tables) and near/med/far splits.
- Both **standard** evaluation and **target-aware** evaluation.
- Analysis via **disentangled IoU3D** (depth vs dimensions vs pose vs XY position) by substituting other attributes with GT.

## What are the main results?

- OVMono3D-LIFT substantially improves over the geometric baseline and prior OV baselines on Omni3D novel categories / novel datasets (and also improves in-domain/base-category performance).
- LIFT beats LIFT\* → geometry/depth features materially matter; their analysis indicates **depth prediction is the main bottleneck**.
- They highlight robustness gains vs GEO in clutter/occlusion.

## How is this similar to GALILEO?

- Strongly aligned with a **decoupled, modular** view: reuse strong pretrained 2D/foundation components and focus learning on the “lifting / 3D reasoning” portion.
- Emphasizes that **evaluation protocols matter** (missing labels / taxonomy ambiguity can dominate “wins”), which is often relevant in open-world settings.

## How is this different from GALILEO?

- Task focus is **metric 3D cuboid detection** from single images (Omni3D-style), not broader open-world 3D scene understanding (depending on GALILEO scope).
- Their open-vocabulary aspect is primarily mediated through **2D detector prompting**, rather than an end-to-end open-vocab 3D model.
- Requires camera intrinsics at inference; notes issues for in-the-wild where intrinsics are estimated.

## Where GALILEO is stronger / cleaner (if true)

- If GALILEO avoids per-image label prompts, it may better reflect a “true open-vocabulary” setting than target-aware evaluation.
- If GALILEO has stronger intrinsic estimation / calibration handling, it may be more practical on in-the-wild images.

## Where GALILEO is weaker / needs to improve

- If GALILEO lacks a principled protocol for missing-label / synonym ambiguity, reported gains may be less reliable.
- If GALILEO’s monocular depth/scale handling is weak, their finding that depth is the bottleneck suggests a likely failure mode.
